# CS 255 System Analysis and Design Portfolio
# DriverPass Project Summary
DriverPass is a client that wanted a web-based system to help students prepare for their driving exams. They were losing potential customers to the DMV because people were showing up unprepared and failing their tests. The system that I designed lets students create accounts, purchase preparation packages, take online practice tests, and schedule in-person driving lessons. It also gives staff tools to manage appointments and keep content up to date.
# What I Did Well
I think I did a good job translating the client interview into actual system requirements and then carrying those requirements through into the UML diagrams. The class diagram especially came out clean and covered all the key objects the system would need without overcomplicating it.
# What I Would Revise
If I could go back and revise one thing, it would be the use case diagram. I think I could have been more specific about the relationships between some of the use cases, particularly around how purchasing a package connects to unlocking certain features like test access and appointment scheduling. Adding include or extend relationships there would have made the design clearer for developers reading it.
# Interpreting User Needs
I went back to the interview transcript a lot while working through both documents to make sure I was actually solving the problems DriverPass described and not just building what sounded good on paper. The client mentioned things like wanting students to be able to practice anywhere and needing staff to manage everything from one place, so those became core requirements. Keeping the user at the center of the design matters because a system that is technically sound but does not match how people actually work is not going to get used the way it was intended.
# My Design Approach
I started by pulling all the requirements out of the interview before touching any diagrams, which helped a lot because it gave me a clear picture of what the system actually needed to do before I started thinking about how to build it. Going forward, I would keep using that same approach of requirements first, diagrams second. I would also spend more time on the class diagram early in the process since it ends up being the foundation that everything else references.
